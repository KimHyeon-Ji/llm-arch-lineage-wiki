# Sparse Attention — 연산 특성과 아키텍처 아이디어 (한 페이지)

> **sparse attention 이후 decode attention의 병목은 "보기(attention)"에서 "찾기(indexer)"와 "가져오기(gather)"로 옮겨 간다.**
> 그래서 필요한 하드웨어는 더 큰 행렬곱기가 아니라 **스캔 엔진 · 선택기 · gather 엔진 · 계층형 KV 메모리**다.

첫 아이디어 논의용 · decode 기준 · 근거와 수치: [세미나 요약 §4–5](../seminar/01-attention-seminar_sum_ver.md) · 수치는 공개 config 기반 개략 계산, 아이디어는 **검증 전 가설**

## 1. 계열 분류 — 무엇을 줄였고, 무엇이 새로 생겼나

| 계열 | 대표 | 줄인 것 | 본 attention이 읽는 단위 | 새로 생긴 연산 | 접근 패턴 |
|---|---|---|---|---|---|
| **고정 창** | SWA (Mistral · Gemma · gpt-oss) | 저장 + 읽기 (`W`로 상한) | 최근 `W`토큰 | 없음 (ring buffer 교체) | **연속** |
| **토큰 선택** | DSA (V3.2 · GLM-5) | 읽기만 (저장 +11%) | 토큰 2,048개 | indexer 스캔 · top-k · **토큰 gather** | 스캔 연속 + **흩어짐** |
| **블록 선택** | QSA (Qwen3.8) · MiniMax M3 | 읽기 + 검색 (저장 그대로) | 4토큰 × 512블록 / 128토큰 × 16블록 | 블록 키 생성 · top-k · **블록 gather** | 블록 안 연속, 블록 사이 흩어짐 |
| **압축 + 선택** | CSA (V4) | 저장 + 검색 + 읽기 | 압축 엔트리 1,024개 | **쓰기 시 압축** · top-k · gather | 흩어짐 (단위는 압축 엔트리) |
| **고압축 + 전부** | HCA (V4) | 저장 + 읽기 (`S/128`) | 엔트리 전부 | **쓰기 시 압축** | **연속** (dense) |
| **선택 공유** | GLM-5.2+ · V4.1 CSA2 | 검색 (여러 층이 top-k 재사용) | 앞 층이 고른 위치 | 없음 — **다음 층 주소를 미리 앎** | 흩어짐, 단 **예측 가능** |

**한 줄로:** 위로 갈수록 연속·단순, 아래로 갈수록 동적·불규칙. 업계는 DSA(토큰 gather)를 정점으로 **다시 연속 쪽으로 되돌아오는 중**이다 — gather를 없애거나(HCA), 단위를 키우거나(QSA), 주소를 재사용한다(층 공유).

## 2. 연산 특성 — 선택형 attention의 5단계

```
[쓰기]          [① 스캔]           [② 선택]        [③ 주소·gather]       [④ 본 attention]
KV·색인키 append → 색인 키 S개 내적 → top-k (비교) → 고른 KV 흩어진 읽기 → 고른 k개에 dense MLA/GQA
(CSA/HCA: 압축)   저정밀 · 연속      행렬곱 아님     행렬곱 아님           헤드 공유 → 재사용 높음
```

| 단계 | 연산 성격 | 바운드 | 배치로 재사용? | 1M 컨텍스트 · 층 하나 수치 (DSA) |
|---|---|---|---|---|
| 쓰기 | append-only, 한 줄 | 쓰기 지연 | — | 읽기 : 쓰기 = `S` : 1 |
| ① 스캔 | FP8/FP4 내적 + ReLU + 헤드 가중합 | **메모리** (~128 FLOP/B, QSA는 헤드 4개라 ~4–8) | **아니오** — 요청별 데이터 | **128 MB = 읽는 바이트의 ~98%** |
| ② 선택 | 1M 점수 → 2,048 top-k, reduction | 비교·제어 (FLOPs에 안 잡힘) | 아니오 | 점수를 HBM에 쓰면 ~4 MB 중간 배열 |
| ③ gather | 데이터 의존 주소, 토큰당 ~1.1 KB (QSA 블록은 수 KB) | **지연 · 요청 동시성** | 아니오 | 2.4 MB, 단 **2,048조각** |
| ④ attention | dense 행렬곱 (MLA 헤드 128 공유) | 연산 쪽에 가까움 (~130–250 FLOP/B) | 아니오 | 바이트는 작고 연산 밀도는 높음 |

**핵심 관찰 5개**

1. **바이트는 스캔이, 시간은 gather가 먹는다** — 스캔은 바이트의 ~98%지만 연속이라 대역폭을 다 쓴다. gather는 2%지만 조각이 많아 실효 대역폭이 낮다. (CSA도 색인 16 MB vs 엔트리 0.6 MB로 같은 구도)
2. **직렬 의존 체인** — 스캔 → top-k → gather는 앞 단계가 끝나야 주소가 나온다. 한 요청 안에서는 겹칠 수 없다
3. **배치가 안 통한다** — 가중치와 달리 색인 키·KV는 요청마다 달라, 배치를 키워도 산술 강도가 그대로다 → PIM/near-memory에 유리한 성격
4. **정확할 필요가 없다** — indexer의 목표는 순위가 아니라 **recall**. 근사 top-k, 저정밀(FP4) 스캔이 허용된다
5. **층마다 성격이 다르다** — V4는 CSA(gather)·HCA(stream)를 1:1 교대, Qwen3.8은 DeltaNet(고정 state를 매 토큰 고쳐 씀) 3 : QSA 1. 한 칩이 **stream · gather · state RMW** 세 패턴을 모두 받아야 한다

## 3. 아키텍처 아이디어

| # | 키워드 | 아이디어 | 근거 (관찰) | 검증할 것 |
|---|---|---|---|---|
| A | **Indexer-in-Memory** | 스캔 + 점수 집계 + 스트리밍 top-k를 HBM 옆(PIM / base die)에서 끝내고 **인덱스 2,048개만** 호스트로. "decode 분리"의 attention판 — *찾기는 메모리, 보기는 GPU* | 1 · 3 · 4 | PIM 연산 밀도로 128 FLOP/B를 감당하나, 전역 top-k 병합 비용 |
| B | **근사·스트리밍 Top-k 유닛** | 히스토그램/radix 기반 임계값 선택, 타일별 top-k + 병합. 점수 배열을 메모리에 쓰지 않음 | 2 · 4 | recall 손실 vs 면적, 1M 길이에서 지연 |
| C | **Index-driven Gather DMA** | 인덱스 리스트 → page table walk(paged KV) → 인접 선택 병합 → SRAM 직행. 수천 개 outstanding read, 채널/뱅크 분산 배치 | 1 · 2 | 실효 BW (유효 바이트 ÷ 전송 바이트), 뱅크 쏠림 |
| D | **요청 간 파이프라인** | 한 요청 안 체인은 직렬이므로 **요청 A gather ‖ 요청 B 스캔 ‖ 요청 C attention**으로 단계별 유닛을 돌림 | 2 | 단계별 시간 균형, 버퍼 용량 |
| E | **선택 기반 Prefetch** | ① 층 공유 모델: 첫 층 top-k로 **다음 층들의 KV를 정확히** prefetch ② 스텝 간 top-k 중복을 이용한 투기적 prefetch ③ 타일 이중 버퍼 | 2 · 선택 공유 계열 | 스텝 간 top-k 중복률(측정 필요), 낭비 대역폭 |
| F | **계층형 KV 메모리** | **색인 키(매 스텝 전부) → HBM**, **본 KV(매 스텝 2,048개만) → 용량 계층**(LPDDR/CXL), 최근 창·압축 대기 state → SRAM. DSA 1M 기준 HBM 색인 ~8 GB, 용량 계층 latent ~70 GB, 토큰당 용량 계층 읽기 ~144 MB (≈ 60 GB/s에서 ~2.4 ms, HBM 스캔과 같은 자릿수) | 1 · 3 | 용량 계층의 KB 단위 랜덤 읽기 효율, 배치 확장 시 대역폭 |
| G | **블록 크기 ↔ 메모리 granule 공동 설계** | 선택 블록 = KV page = 버스트/CXL 라인 배수. QSA(4토큰)·MiniMax(128토큰)처럼 단위를 HW에 맞춰 고르는 **모델-HW co-design** | 1 | 블록이 커질수록 과다 읽기 · 품질 |
| H | **Compress-on-Write 엔진** | CSA/HCA는 블록이 차면 softmax 가중 합으로 엔트리 생성 → 쓰기 경로 전용 소형 연산기 + 요청별 고정 크기 state를 SRAM 상주 | 5 | 요청 수 × state 크기가 SRAM에 들어가나 |
| I | **이종 decode 칩** | dense stream 유닛 + sparse gather 유닛 + state RMW 유닛(DeltaNet)을 한 칩에. 층 종류별로 스케줄 | 5 | 층 비율이 모델마다 다름 → 유연성 vs 효율 |

## 4. 첫 논의에서 정할 것

- **어디부터 팔까** — 바이트 대부분을 먹는 **A(스캔)** vs 시간 효율이 나쁜 **C(gather)** vs 용량 문제를 푸는 **F(계층 메모리)**
- **측정 1순위** — 같은 모델·같은 `S`에서 단계별 시간 분해 (스캔 / top-k / gather / attention), gather 실효 대역폭, 스텝 간·층 간 top-k 중복률
- **주의** — 짧은 컨텍스트(< 수만 토큰)에서는 선택 오버헤드가 이득보다 클 수 있다. 전체 decode 시간은 가중치 읽기·MoE 통신과 함께 봐야 한다
- **prefill은 별도** — indexer가 `T × S` 행렬곱이 되어 compute 쪽으로 이동. 위 아이디어는 decode 경로 한정
