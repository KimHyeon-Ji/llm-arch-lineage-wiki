# Sparse·Hybrid Attention — 정량 분석 및 발표 자료 기획

작성일: 2026-11-06 · 대상: 알고리즘 상세보다 아키텍처 판단에 필요한 핵심을 보는 의사결정자 · [Claude 계획안](00-deck-plan-claude.md) 검토 반영

**주제: 차세대 아키텍처 탐색을 위해, 최근 주요 AI 모델의 sparse·hybrid attention 구조와 동작 특성을 정량적으로 분석한다.**

> **최종 산출물은 PPT 본문 6장. 한 장에 질문 하나, 주 그림 하나, 설명은 한 문장씩 최대 3개.**
> 숫자는 “얼마나 줄었나”, 그림은 “어떤 동작이 남았나”, 결론은 “그래서 어떤 하드웨어를 검토하나”로 연결한다.

## 1. 전달할 이야기

발표를 듣고 다음 세 질문에 답할 수 있으면 된다.

1. **무엇이 바뀌었나?** 전체 과거를 읽던 방식에서 선택 조회·압축·고정 크기 요약 상태로 바뀐다.
2. **무엇을 얼마나 줄였나?** 읽기량·저장량·연산량을 각각 보고, 새로 생긴 선택·주소 처리·상태 갱신 비용을 더한다.
3. **아키텍처에 무엇을 요구하나?** 대역폭·용량·불규칙 접근·자주 갱신하는 상태 중 어디에 투자할지 좁힌다.

도입은 익숙한 **FFN → MoE**에 빗댄다.

| 익숙한 MoE | Sparse attention에 대응하는 관점 |
|---|---|
| 모든 계산 대신 일부 전문가를 활성화 | 전체 과거 대신 일부 KV를 조회 |
| 전체 전문가의 가중치는 여전히 보유 | 선택 조회형은 전체 KV도 여전히 보유할 수 있음 |
| 라우팅·데이터 이동 비용이 추가 | 색인 검색·top-k·흩어진 KV 읽기 비용이 추가 |

비유 뒤에는 차이를 한 문장 붙인다. **가중치는 요청들이 공유하지만, KV·요약 상태는 기본적으로 요청마다 따로 생긴다.** 따라서 동시 요청 증가가 메모리에 주는 영향도 다르다. MoE는 전문가 집합에서, 색인 기반 sparse attention은 길이에 따라 늘어나는 과거 후보에서 고른다는 차이도 짚는다.

발표 멘트에서는 **KV=녹취록, sparse=색인으로 필요한 부분 조회, 압축=구간별 요약본, recurrent state=계속 고쳐 쓰는 요약 노트**로 설명한다. 이 비유는 동작 이해에만 쓰고, 정확도나 속도 우열은 수치로 확인한다.

## 2. PPT 6장 구성

| 장 | 제목·핵심 질문 | 주 그림과 비교 기준 | 전달할 메시지 |
|---|---|---|---|
| **1** | **MoE가 전문가를 고르듯, Sparse는 읽을 과거를 고른다** | FFN→MoE / Full→Sparse를 나란히 놓은 간단한 선택 그림 | 활성 부분이 줄어도 보유 용량과 선택 비용은 남는다 |
| **2** | **원본 선택·이력 압축·요약 상태는 줄이는 대상이 다르다** | 네 가지 동작 카드 + Hybrid의 층 구성 띠 그림 | 원본을 골라 읽기, 묶어 저장하기, 요약 상태로 갱신하기를 구분 |
| **3** | **읽는 양과 저장하는 양은 따로 줄어든다** | 왼쪽: decode 읽기량 누적 막대 **MiB/쿼리/층**. 오른쪽: 보유량 막대 **MiB/요청/층** | 같은 길이에서 본 KV·색인·고정 상태를 모두 포함해 비교 |
| **4** | **적은 KV를 읽기 위해서도 찾기·선택·갱신 비용이 든다** | 방식별 가로 누적 막대: 색인 읽기 / 선택 KV / 최근 창 / state 읽기 / state 쓰기. **MiB/스텝/층** | 바이트의 주역과 시간의 주역을 구분. top-k 비교 비용은 시간·연산 수로 보충 |
| **5** | **읽기 절감에도 검색 비용이 정하는 한계가 있다** | X: 문맥 길이, Y: Full 대비 **읽기 절감 배수**. **1× 선**과 긴 구간의 추세 표시 | 선택량이 고정돼도 색인 스캔은 증가한다. 포화 수준·이득 시작점은 구조·정밀도에 따라 계산 |
| **6** | **크게 보관하는 데이터와 자주 고치는 상태는 요구가 다르다** | **메모리 성격 지도:** X=스텝당 논리 읽기 비율, Y=보유량, 점 모양=쓰기 방식. 후보 3개를 주석으로 연결 | 선택·gather 지원, KV 용량 계층, 갱신 상태의 온칩 보관 중 우선순위 제안 |

**기법 설명은 2장에서 끝내고, 이후에는 비교군 이름으로만 사용한다.** Full(GQA/MLA), 토큰 선택(DSA), 블록 선택(QSA·NSA/MoBA), 압축(CSA/HCA)을 구분하고, Hybrid는 고정 상태 층과 KV 조회 층의 조합으로 보여준다. HCA의 압축 이력 조회는 dense다. [세미나 §4–5](../seminar/01-attention-seminar_sum_ver.md), [QSA·GDN hybrid 원문 §2.1](https://arxiv.org/html/2608.30320v1), [CSA/HCA 원문 §2.3](https://arxiv.org/html/2606.19348v1)

**3장은 층의 동작을 비교하고, Hybrid 전체 모델은 실제 층별 비용을 합산한다.** 고정 상태 층 한 개를 KV 조회 층 한 개와 비교한 결과만으로 모델 전체 절감률을 정하지 않는다.

**4장의 막대는 Read+Write 이동량**이며, 3장의 읽기량과 구분한다. byte가 작은 top-k·주소 처리도 시간이 들기 때문에 막대 비중만으로 병목을 결론 내리지 않는다. **5장의 읽기 절감 배수와 실측 속도 배수도 구분**한다. 같은 조건의 성능 근거가 확보되면 속도 곡선을 보충하고, Prefill/Decode와 레이어/모델 전체를 별도 패널로 표시한다.

추가 장이 필요하면 **배치 증가에 따른 가중치/KV 읽기 비중**을 우선 보충한다. MoE 가중치는 batch가 실제로 방문하는 전문가 합집합과 재사용을 반영해 계산한다. 채택 추이 차트는 공개 표본·기간·중복 분류 기준을 확인한 뒤 부록에 두고, 본문은 6장을 유지한다.

## 3. 정량 분석 기준 — 숫자의 분모를 먼저 고정

| 항목 | 기본 기준 |
|---|---|
| Decode | 요청 1개·새 토큰 1개·층 1개. **쿼리 1개는 해당 토큰의 모든 query head를 포함** |
| Prefill | 프롬프트 전체 처리 비용·시간. Decode의 토큰당 비용을 그대로 곱하지 않음 |
| 길이 | 막대의 핵심 비교는 **128K·1M**, 32K는 짧은 문맥 점검용. 곡선은 지원 범위에서 촘촘히 계산. K=1,024로 통일 |
| 비교 두 종류 | **구조 효과:** 동일 KV 정밀도·가능한 공통 차원으로 통제한 계산. **실제 사례:** 각 모델의 공개 구성·층 수·실제 dtype으로 계산. 그림을 분리 |
| 포함할 상태 | 본 KV + 색인 + 최근 window + 압축 대기 + recurrent/conv state. 공유된 저장은 한 번만 집계 |
| 단위·근거 | 저장은 MiB/GiB, 이동은 MiB/스텝, BW는 GB/s. **계산값·문헌 실측·직접 실측** 표시 |

모든 차트의 부제에 **단계·층/모델 범위·길이·batch·정밀도·기준 방식**을 한 줄로 쓴다. 예: “Decode · 층당 · 1M · B=1 · KV BF16 환산 · 동일 KV 표현의 Full 대비”. 수치의 뜻이 다른 단위는 각 축에 표시한다.

비용은 **색인 검색 → 선택(top-k) → KV 가져오기 → attention**, 그리고 **KV 추가·압축·상태 갱신**으로 나눈다. 선택 연산은 비교·주소 처리도 필요하므로 FLOPs만으로 평가하지 않는다.

**읽어야 할 논리 바이트와 실제 HBM 전송량을 구분한다.** 페이지 과다 읽기·재읽기·온칩 재사용은 구현에 따라 달라진다. BW는 실측 전송량÷해당 시간, 목표 필요 BW는 전송량÷허용 시간으로 산정한다. 계산한 읽기량 감소 배수를 속도 배수로 쓰지 않는다.

시간을 환산할 때는 선택한 장치의 공식 BW와 가정을 적고 **이상적인 I/O 시간 하한**으로 표시한다. 속도 그래프는 같은 장치·batch·정밀도·기준 구현을 고정한다. 레이어 시간, 모델 전체 첫 토큰 시간(TTFT), 이후 토큰 생성 시간(TPOT)을 구분한다. 조건이 다른 공개 결과는 별도 패널로 둔다.

## 4. 메모리 동작에서 아키텍처 인사이트를 뽑는다

| 데이터 | 추론 중 동작·증가 특성 | 검토할 아키텍처 방향 |
|---|---|---|
| **가중치** | 값은 바뀌지 않고 반복 읽기; 요청 간 공유 | 여러 요청·토큰의 재사용, 연산기로 공급할 대역폭 |
| **과거 KV** | 기존 부분 반복 읽기 + 새 토큰 끝에 추가; 요청·길이에 따라 증가 | KV 용량 계층, page 배치, gather DMA·동시 read·prefetch |
| **색인·블록 요약 키** | 반복 스캔 + 새 항목 추가; 선택형의 보조 저장 | 스캔·점수 집계·top-k 결합, 메모리 근처 선택 처리 |
| **고정 크기 요약 상태** | 매 토큰 읽고 갱신; 기본 decode 상태 크기는 길이와 무관, 요청 수에 비례 | SRAM 상주 가능성, 읽기·쓰기 처리량, 갱신 연산 결합 |

여기서 **read-only는 추론 중 값이 바뀌지 않는다는 동작 특성**이다. 곧바로 ROM 같은 별도 메모리 소자를 뜻하지 않는다. 상태 갱신도 매번 HBM을 왕복한다는 뜻은 아니므로, 온칩에 유지할 수 있는 크기인지 확인한다. Hybrid에서 서로 다른 상태의 관리가 필요한 구현 사례는 [vLLM Hybrid KV Cache Manager](https://docs.vllm.ai/en/latest/design/hybrid_kv_cache_manager/)를 참고한다.

**6장의 지도는 모델 복제본 1개·B=1·길이 고정**으로 그린다. X축은 해당 스텝에 읽는 고유 논리 byte÷보유 byte이며, 물리 BW 사용률과 구분한다. 가중치는 모델 공유, KV·상태는 요청 전용임을 점 옆에 표시한다. 작은 조회 비율은 용량 계층을 검토할 근거지만, 실제 이동량·접근 지연·동시 요청 부하를 확인해야 한다. SRAM 후보도 **요청 수×상태 크기**가 들어가는지 계산한다.

**최종 후보는 관측값으로 고른다:** 스캔·선택 지연이 크면 selector, KV 가져오기 지연이 크면 gather/prefetch, 상태 용량·쓰기 부담이 크면 메모리 계층·온칩 상태 관리를 우선 검토한다. 상세 아이디어는 [기존 아키텍처 노트](01-sparse-attention-arch-insight.md)에 둔다.

## 6. 차트·원고 작성 규칙

- **제목은 결론 문장**, 부제는 비교 조건, 본문은 그림 하나와 설명 최대 3줄로 고정한다. 초안의 결론은 계산 결과에 맞춰 수정한다.
- 한 그래프는 **비교군 4개 이하**로 제한하고, 이름은 막대 옆·선 끝에 직접 붙인다. Full 회색 / 선택 파랑 / 압축 주황 / 고정 상태·Hybrid 초록을 일관되게 쓴다.
- 강조 숫자는 장당 하나만 크게 쓴다. 계산·문헌 실측·직접 실측은 **명시적 라벨·점 모양**으로 구분한다.
- 지원 길이 밖의 곡선이 필요하면 **비용 계산 외삽만 점선**으로 표시한다. 외삽 구간에 정확도·실행 가능성·실측 속도 의미를 부여하지 않는다.
- 마지막에 제목 6개만 이어 읽어 흐름을 점검한다. “무엇을 줄였고, 무엇이 남으며, 어떤 HW가 필요한가”가 남으면 된다.

LSA 자료에서 가져올 것은 **간단한 제안 그림, 설명 3줄, 읽기량/저장량 막대의 분리, 조건이 명확한 속도 그래프, 적용 구간의 명시**다. 사용자 메모의 LSA 수치는 원문·실험 조건을 확인한 뒤 사용한다. Attention 질량 분포도 실제 데이터가 있을 때 그래프로 만들고, 품질 유지의 근거는 별도 정확도 평가로 확인한다.

수식 유도·전체 모델 목록·커널 세부·세부 하이퍼파라미터는 부록으로 보낸다. 방식 비교표도 **선택 비용 / 읽는 대상 / 보유량 / 원본 KV 접근 여부 / 갱신 방식**만 남겨 부록 한 장으로 만든다. **본문의 판단 기준은 “어떤 동작이 얼마를 차지하며, 어떤 HW 요구로 이어지는가”다.**

기존 자료 재사용: [세미나 요약](../seminar/01-attention-seminar_sum_ver.md)의 구조 설명, [메모리 요구량 보고서](../reports/llm-memory-requirements.md)의 용량·모델 구성, [Linear attention 정리](../02-linear-attention.md)의 고정 상태·Hybrid 설명. 기존 수치도 분석 조건이 맞는지 확인해 사용한다.
