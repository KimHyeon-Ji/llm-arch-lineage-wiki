## 1. 이야기 구조 — 질문 셋, 메시지 셋

덱은 세 막으로 간다. 상사가 헤드라인만 읽어도 각 질문의 답이 남아야 한다.

| 막 | 질문 | 답 (메시지) |
|---|---|---|
| **1. 무엇이 바뀌었나** | attention이 어떻게 달라지고 있나? | **최신 모델은 "과거를 전부 읽는 attention"을 버리고 있다.** 고르고(sparse), 묶고(압축), 요약 상태로 바꾼다(hybrid). 2026 H2 공개 15개 중 14개 |
| **2. 무엇을 얼마나 줄였나** | 읽기 · 저장 · 연산이 각각 얼마나 줄었고, 무엇이 새로 생겼나? | **읽기는 1/10 ~ 1/100로 주는데, 저장은 그대로인 방식이 많다.** 대신 찾기(색인 스캔) · 고르기(top-k) · 흩어진 읽기 · 상태 갱신이 새 비용이 된다 |
| **3. 아키텍처에 무엇을 요구하나** | 대역폭 · 용량 · 불규칙 접근 · 갱신 상태 중 어디에 투자하나? | **"더 빠른 HBM" 하나가 아니라, 데이터 성격별 메모리 계층 + 찾기 · gather 경로가 필요하다** |

**도입은 MoE로 연다.** "MoE가 FFN에서 일부 expert만 쓰듯, sparse attention은 과거 토큰 중 일부만 읽는다." 그리고 바로 차이를 붙인다. **"가중치는 요청들이 공유하지만, KV와 요약 상태는 요청마다 따로 생긴다."** (§4)

> 결론 슬라이드의 틀: **prefill → 연산(GPU) · decode → 메모리 대역폭 · MoE → 네트워크 · sparse attention → 메모리 계층과 gather · hybrid → 온칩 상태와 쓰기 대역폭**

## 2. 분석 기준 — 숫자의 분모를 먼저 고정

참고 자료(LSA 설명 자료)처럼 **기준을 차트 부제에 한 줄로 고정**한다.

| 항목 | 기준 | 표기 예 |
|---|---|---|
| decode 읽기 · 쓰기 | **요청 1개 · 새 토큰 1개 · 층 1개.** 쿼리 1개는 그 토큰의 query head 전부를 포함 | "디코드 1스텝, 층당" |
| 저장 | **요청 1개 · 층 1개 · 컨텍스트 `S`** | "층당, 1M 컨텍스트" |
| 연산 | **쿼리 1개당** — 고르는 비용과 attention 계산을 나눠서. top-k는 FLOPs가 아니라 비교 · 주소 처리로 따로 센다 | "쿼리당" |
| prefill | 프롬프트 전체를 처리하는 비용 · 시간. decode의 토큰당 비용을 곱해서 만들지 않는다 | "프롬프트 1M, 층당" |
| 컨텍스트 | 막대는 **32K · 128K · 1M** 세 점 (모델의 공개 지원 길이 안), 곡선은 8K ~ 10M (지원 밖은 점선) | |
| 포함할 상태 | 본 KV + 색인 키 + 최근 window + 압축 대기 + recurrent · conv state. **층끼리 공유하는 저장은 한 번만** 센다 | |
| 단위 | **GB = 10⁹ B** (세미나 · 메모리 보고서와 같게). 대역폭은 GB/s | |
| 근거 표시 | 모든 숫자에 **계산값 · 문헌 실측 · 직접 실측** 중 하나를 붙인다 | 실선 = 계산, 점 = 실측 |

**비교는 두 종류로 나누고, 그림도 나눈다.**

| | 구조 효과 | 실제 사례 |
|---|---|---|
| 목적 | 방식 자체가 무엇을 줄이나 | 실제 모델에서 얼마나 줄었나 |
| 조건 | KV 정밀도 BF16 통일, 선택 예산 같게 (2,048토큰), **층 하나**끼리 비교 | 공개 config의 층 수 · 층 구성 · 실제 dtype으로 **모델 전체 합산** |
| 주의 | hybrid는 "state 층 하나 vs KV 층 하나" 비교로 모델 전체 절감률을 말하지 않는다 | V4처럼 구조 + 정밀도 효과가 섞이면 따로 표기 |

**바이트와 시간을 섞지 않는다.**

- **논리 바이트**(읽어야 할 양)와 **실제 HBM 전송량**(페이지 과다 읽기 · 재읽기 · 온칩 재사용 반영)을 구분한다
- **읽기 감소 배수를 속도 배수로 쓰지 않는다.** 시간은 "바이트 ÷ 대역폭 = 하한"으로만 쓰고, 실측이 있으면 따로 붙인다
- 속도 그래프는 장치 · batch · 정밀도 · 기준 구현을 고정하고, **층 시간 · 첫 토큰 시간(TTFT) · 토큰 생성 시간(TPOT)** 을 나눈다. 조건이 다른 공개 결과는 별도 패널로 둔다

## 3. 슬라이드 구성

본문 7장 + 선택 2장 + 부록. 각 장은 **제목 = 질문, 헤드라인 = 답**, 차트 1개, 불릿 3개.

| # | 질문 → 헤드라인 (초안) | 차트 | 불릿 3개 (초안) | 데이터 |
|---|---|---|---|---|
| **1** | 무엇이 바뀌고 있나? → **2026년 대형 모델 대부분이 '전부 읽기'를 버렸다** | 반기별 누적 막대: 모델 수 × 분류 4종 (full / sparse / window / state) | ① 2026 H2 15개 중 full만 쓰는 모델은 1개 ② 회사마다 경로는 달라도 방향은 같다 ③ 공통 목적은 KV를 덜 저장하고 덜 읽는 것 | 메모리 보고서 ✅ |
| **2** | 익숙한 것에 빗대면? → **Sparse attention은 'attention의 MoE'다 — 다만 고를 대상이 다르다** | 좌우 그림: FFN → MoE / Full → Sparse 같은 모양 + 아래 비교표 3줄 (§4) | ① 둘 다 작은 선택기(router / indexer)가 일부만 골라 쓴다 ② 둘 다 고르지 않은 것도 **전부 보유**한다 ③ 다른 점: MoE는 고정된 expert 수백 개를 요청들이 공유, sparse는 **요청마다 따로 자라는 토큰 수백만 개**에서 고른다 | 정성 + 수치 ✅ |
| **3** | 방식은 무엇이 다른가? → **골라 읽기 · 묶어 저장하기 · 요약 상태로 바꾸기, 그리고 층마다 섞는다** | 위: 동작 카드 4장 (전부 읽기 / 골라 읽기 / 묶기 / 요약 상태) · 아래: **층 구성 띠** — V3.2 (DSA 61층) · V4 (CSA · HCA 교대) · Qwen3.8 (DeltaNet 3 : QSA 1) · gpt-oss (window 1 : full 1) | ① 골라 읽기(DSA · QSA)는 원본을 그대로 두고 읽을 곳만 고른다 ② 묶기(CSA · HCA)와 요약 상태는 저장 자체를 줄인다 ③ 최신 모델은 한 가지가 아니라 **층마다 다른 방식을 섞는다** (= hybrid) | 세미나 ✅ |
| **4** | 무엇을 얼마나 줄였나? → **디코드마다 읽는 양은 1/10 ~ 1/100, 저장은 그대로인 방식이 많다** | 두 막대 나란히 (LSA 자료 (5)형) · 왼쪽: 1스텝 읽기를 **동작별 누적** (색인 스캔 / 고른 KV / 최근 창 / state) · 오른쪽: 저장 · 층당, 1M, 구조 효과 기준 | ① DSA는 읽기 1/9, 저장 +11% ② **줄어든 읽기의 약 98%는 '찾기'(색인 스캔)** 다 ③ 묶기 · 요약 상태는 저장까지 줄이지만, 골라 읽기는 수 M 토큰 KV를 담을 **용량**이 여전히 필요하다 | §6 ✅ / 일부 확인 |
| **5** | 언제 이득이고, 어디서 막히나? → **긴 컨텍스트에서만 이득이고, 절감에는 천장이 있다** | 로그-로그 선: x = 컨텍스트 8K ~ 10M, y = Full 대비 읽기 절감 배수, **1× 선** 표시 · 작은 패널: prefill / decode 공개 속도 (조건 명시) | ① 수만 토큰 이하에서는 이득이 작거나 손해다 ② DSA는 길어져도 **약 9배에서 멈춘다** (= 본 KV 크기 ÷ 색인 키 크기) — 다음 경쟁은 찾기 비용 줄이기 (압축 색인 · 블록 색인 · 층 간 공유 · LSA) ③ prefill은 연산이 병목이라 이득의 모양이 다르다 | 계산 스크립트 필요 · 속도는 문헌 |
| **6** | 데이터는 어떻게 읽고 쓰나? → **읽기만 하는 것, 한 번 쓰고 계속 읽는 것, 매번 고쳐 쓰는 것 — 필요한 메모리가 다르다** | 데이터 4행 (가중치 / KV / 색인 키 / state) × **읽기 · 쓰기 화살표, 굵기 = 스텝당 바이트**, 옆에 보유량 | ① 가중치와 색인 키는 매번 전부 읽는다 → 대역폭 ② sparse의 본 KV는 크지만 매번 **0.2%만** 읽는다 → 용량 계층 후보 ③ state는 작지만 매 스텝 전부 다시 쓴다 (Qwen3.8-27B: state 0.15 GB 덮어쓰기 vs KV 66 KB 추가) → 온칩 · 쓰기 대역폭 | §5 ✅ |
| **7** | 그래서 무엇을 검토하나? → **sparse · hybrid의 병목은 연산이 아니라 찾기 · 흩어진 읽기 · 용량 · 상태 갱신이다** | 그림: 관측된 동작 → HW 요구 → 후보 3개 · 아래 워크로드별 HW 표 (§1 결론 틀) | ① 후보 1 — 계층형 KV 메모리 (색인은 HBM, 본 KV는 용량 계층) ② 후보 2 — 메모리 근처 색인 스캔 + top-k ③ 후보 3 — gather · prefetch 전용 경로 / 온칩 상태 관리 · 우선순위는 단계별 측정으로 정한다 (§8 판단 규칙) | [01 아이디어 문서](01-sparse-attention-arch-insight-claude.md) |
| 선택 A | 왜 지금 문제인가? → **배치가 커지면 decode 읽기의 주인이 가중치 → KV로 바뀐다** | 묶음 막대: 배치 1 · 4 · 32에서 스텝당 읽기 (가중치 / KV), V3 vs V3.2, 128K | ① 가중치는 배치가 나눠 읽고, KV는 요청마다 따로 읽는다 ② 전부 읽는 V3는 **배치 4**에서 KV가 가중치(약 37 GB)를 넘는다 ③ DSA를 쓴 V3.2는 **배치 32**까지 버틴다 | ❌ **보류** — MoE는 배치가 커지면 고르는 expert의 합집합이 커져 가중치 읽기도 늘어난다 (V3 균등 routing 가정: 배치 1 약 38 GB → 배치 32 약 430 GB). "가중치 37 GB 고정" 가정이 틀리므로 dense 모델 예시나 실측 routing으로 다시 만든다 |
| 선택 B | 적게 읽는데 왜 안 빠른가? → **읽는 개수보다 조각 수가 속도를 정한다** | 같은 2,048토큰을 2,048조각(DSA) · 512조각(QSA) · 연속(HCA)으로 읽는 그림 + 실효 대역폭 | ① 고른 KV는 컨텍스트 여기저기 흩어져 있다 ② top-k는 FLOPs로 세어지지 않는 비교 작업이다 ③ 업계는 gather를 없애거나(HCA) 단위를 키운다(QSA) | 세미나 ✅ / 실효 BW는 실측 |
| 부록 | 방식 비교표 (§7) · 계산식 · 가정 · 모델별 수치 · 메모리 성격 버블 차트 (x = 읽는 비율, y = 크기) | | | |

**원고 반영 (2026-11-06):** 2장 뒤에 "KV cache = 토큰 수 × 토큰당 차원 표, 방식마다 줄이는 축이 다르다" 슬라이드를 넣었다 (청중 반응이 좋았던 세미나 그림 `26-axes`를 덱 색 체계로 다시 그린 `figures-claude/03-kv-axes`). 위 3장은 "층마다 섞는다(hybrid)"로 좁혀 본문이 8장이 됐다.

**원고 반영 2차:** 배경 설명을 2장(구조 동향 · KV cache 두 축)으로 줄이고 특성 분석 위주로 재구성했다 — 본문 7장: ① 구조 동향 ② 동작 구조 ③ KV cache 읽기 · 크기 ④ 길이별 효과와 한계 ⑤ KV 접근 패턴(조각 수, 신규 그림) ⑥ 데이터별 메모리 접근 특성 ⑦ sparse attention 아키텍처 시사점. MoE 비교와 층 구성 띠는 부록으로 옮겼다. 이후 MoE 비교는 다시 본문 2장으로 올려 본문 8장(① 구조 동향 ② MoE 비교 ③ 동작 구조 ④ ~ ⑧ 특성 · 시사점), 부록은 층 구성 · 방식별 비교 · 계산 기준이 됐다. 8장은 검토 후보 대신 "단계별 특성 및 관련 시스템 요소"(단계 × 메모리 특성 × 병목 × 관련 HW · 시스템 요소 표)로 바꿨다. 검토 후보는 [01 아이디어 문서](01-sparse-attention-arch-insight-claude.md)에만 둔다. 이어서 정량 분석 장 "8. 메모리 용량 · 대역폭 제약 분석"(H200 × 8에서 동시 1M 요청 수의 용량 한계 vs 대역폭 한계, KV cache를 대용량 계층으로 내린 경우)을 추가해 본문 9장이 됐다. 계산은 `figures-claude/make_figures.py`의 `concurrency()`.

**원고 반영 3차 (리뷰 피드백, 2026-11-06):** 128K를 공통 비교 조건, 1M을 차세대 시나리오(V3.2 · Qwen3.8은 외삽)로 분리. 지원 길이 밖은 점선. 배포 시나리오는 V3.2 실제 형식(KV FP8 656 B, 색인 132 B). 본문 18장 — 동향 · 가중치 vs KV · MoE · 동작 구조 · 층 구성 · 읽기/크기(128K) · 길이별 효과 · 절감 상한 · 색인 산술 강도 · 접근 패턴/증폭 · hybrid 합산 · 메모리 특성 · 접근 밀도 · 동시 요청 수 제약 지도 · 병목 사다리 · 민감도 · 부분 최적화 · 단계별 검증 제약. 계산은 `make_figures.py`의 `solve()` · `step_times()`.

**원고 반영 4차 (구성 재편, 2026-11-10):** sparse attention의 구성 요소(KV cache · 색인)를 장으로 나누고 hybrid를 별도 장으로 뺐다 — Ⅰ 구조 개요(동향 · 방식별 KV cache 쓰기 · 읽기 · 층 구성 · 가중치 + KV 규모 · MoE · 디코드 읽기 구성) → Ⅱ KV cache(읽기 · 크기 · 길이별 · 접근 패턴과 증폭) → Ⅲ 색인(절감 포화 · 연산 특성) → Ⅳ Hybrid(모델 전체 합산 · sparse와 역할 분담) → Ⅴ 종합(데이터별 메모리 특성 · 단계별 특성과 예상 제약). 본문 15장. 3차의 접근 밀도 · 동시 요청 수 지도 · 병목 사다리 · 민감도 · 부분 최적화는 제외(`solve()` 삭제). 동작 구조는 알고리즘(MLA · DSA)이 아니라 방식(전부 · 선택 · 압축 · window · state)별 쓰기 · 읽기로 다시 그렸다.

**원고 반영 5차 (그림 피드백, 2026-11-10):** 2.3은 읽기 증폭 · IOPS를 빼고 "GPU가 약한 작고 · 흩어지고 · 늦게 정해지는 읽기"로 재구성(읽기 단위 · 위치 결정 시점 · GPU 관점 + 특징 → 영향 3가지). 3.1은 곡선 대신 Full 대비 % 누적 막대(선택된 KV + 색인 키 11.5% 바닥)와 같은 색의 "KV 1줄 중 색인 키 몫" 막대로 연결. 3.2는 범례 색 통일 · prefill 패널 삭제. 4.1 · 5.1 · 5.2 그림에 측정 대상 제목 추가, 5.1에 데이터 성격(특성) 열, 5.2는 층당 기준 명시 · 단계별 불릿 · 모델(DSA · QSA · CSA) × 길이(32K · 128K)별 색인 훑기 비중 패널(`stage_reads()`).

**6장으로 줄일 때:** 1장의 트렌드를 3장 동작 카드에 "채택 모델 수"로 넣고 1장을 뺀다.

**LSA 자료에서 가져올 형식:** 간단한 제안 그림 + 설명 3줄, 읽기량 / 저장량 막대 분리, 조건이 명확한 속도 그래프, **적용 구간 명시**("1M 이상 확실 · 512K ~ 1M 본전 · 512K 미만 손해" 같은 구간 서술 → 5장 불릿에 사용). LSA 수치 자체는 원문과 실험 조건을 확인한 뒤에만 쓰고, attention 질량 분포 그래프는 실제 데이터가 있을 때만 만든다.

**비전문가용 비유 (말로 설명할 때)** — KV cache = 회의 녹취록 전체 · Full = 매 문장마다 녹취록을 처음부터 다시 읽음 · Sparse = 색인을 훑고 필요한 쪽만 펼침 · 압축(CSA · HCA) = 4쪽 · 128쪽씩 요약본을 만들어 둠 · Linear(state) = 녹취록 대신 크기가 정해진 요약 노트 한 장을 계속 고쳐 씀 · 하이브리드 = 노트 3권 + 녹취록 1권

## 4. MoE에 빗대기 — 같은 점과 다른 점 (슬라이드 2 원고)

| | FFN → **MoE** | Full → **Sparse attention** |
|---|---|---|
| 무엇을 고르나 | expert (**가중치**) | 과거 토큰 (**KV**) |
| 고르는 장치 | router — 작은 선형층 | indexer — 작은 attention |
| 고르지 않은 것 | 전부 보유 | 전부 보유 (선택형 기준. 압축형은 줄임) |
| 후보 수 | 고정, 수백 개 (V3: 256) | **컨텍스트만큼, 계속 증가** (1M → 100만 개) |
| 고르는 비용 | 무시할 만함 | 후보 수에 비례 — **읽기의 대부분** |
| 한 번에 가져오는 단위 | expert 하나 수십 MB (V3 약 44 MB, FP8) | 토큰 하나 약 1 KB |
| 데이터 성격 | 읽기 전용 · 모든 요청 공유 · 고정 | 한 번 쓰고 계속 읽음 · **요청마다 다름** · 계속 자람 |
| 배치로 재사용 | 됨 — 같은 expert를 여러 토큰이 | **안 됨** |
| 시스템 병목 | all-to-all 통신 · 부하 불균형 | 찾기 스캔 · 흩어진 읽기 · KV 용량 |
| 시사하는 HW | 네트워크 | 메모리 계층 · gather |

> **한 줄:** MoE는 "큰 덩어리 몇 개를 여럿이 함께 고른다", sparse attention은 "작은 조각 수천 개를 요청마다 따로 고른다".
> 공통 시사점: 선택형 구조는 **계산과 읽기는 줄이지만 보유량은 줄이지 않는다** → 용량과 대역폭을 분리해서 설계할 여지가 생긴다

슬라이드에는 위 표에서 **3줄만** 쓴다 (고르는 대상 · 후보 수 · 배치 재사용). 나머지는 부록으로.

## 5. 메모리 동작 지도 — 쓰기 방식 × 읽는 비율 (슬라이드 6 원고)

| 데이터 | 쓰기 방식 | 스텝당 읽는 비율 | 크기 (요청 1개, 1M, 전 층) | 검토할 방향 |
|---|---|---|---|---|
| 가중치 (dense · shared) | **추론 중 바뀌지 않음** | 100% (배치가 나눠 읽음) | 수십 ~ 수백 GB, 요청과 무관 | 대역폭 · 배치 재사용 |
| 가중치 (MoE expert) | 바뀌지 않음 | 활성분만 (V3 약 5%), 배치가 크면 늘어남 | 위와 같음 | 대역폭 · 네트워크 |
| KV — full | **한 번 쓰고 계속 읽기** (끝에 추가) | 100% | 74 GB (MLA · V3) | HBM 대역폭 |
| KV — sparse 본체 | 한 번 쓰고 계속 읽기 | **약 0.2%** (2,048 / 1M) | 74 GB (V3.2) | **용량 계층 · page 배치 · gather · prefetch** |
| 색인 키 | 한 번 쓰고 계속 읽기 | 100% (순차 스캔) | 약 8 GB (V3.2) | HBM · 메모리 근처 스캔 + top-k |
| 압축 KV (V4) | 블록이 차면 묶어서 쓰기 | CSA 일부 · HCA 100% | 약 5 GB (V4-Pro) | 압축 연산 · 순차 읽기 |
| 최근 창 · 압축 대기 | **링 버퍼 덮어쓰기** | 100% | 수 MB (고정) | 온칩 상주 |
| Linear state (DeltaNet 등) | **매 스텝 전체 다시 쓰기** | 100% 읽기 + 100% 쓰기 | 약 0.2 GB (Qwen3.5, 고정) | 읽기 · 갱신 · 쓰기 결합, 쓰기 대역폭 |

- **"읽기 전용"은 동작 특성이다.** 추론 중 값이 바뀌지 않는다는 뜻이지, ROM 같은 별도 소자를 쓰자는 뜻이 아니다
- **KV는 고치지 않는다(immutable).** 써 둔 줄은 바뀌지 않으므로 하위 계층으로 내려도 일관성 문제가 없고, 쓰기 대역폭도 거의 필요 없다 (읽기 : 쓰기 = `S` : 1)
- **state는 정반대다.** 작지만 매 스텝 전부 읽고 전부 쓴다. 단, **층 하나 · 요청 하나는 약 4 MB라 온칩에 들어가지만, 요청 전체(약 190 MB) × 동시 요청 수는 HBM에 둬야 한다.** 그래서 관건은 "SRAM에 상주"보다 **층 단위로 읽고-갱신하고-쓰기를 한 번에 묶는 것**과 쓰기 대역폭이다 — 실제로 들어가는지 크기로 확인한다
- **sparse가 처음으로 "크지만 드물게 읽는" 데이터를 만들었다.** 이것이 메모리 계층을 나눌 근거다
- 서로 다른 상태를 함께 관리하는 구현 사례: [vLLM Hybrid KV Cache Manager](https://docs.vllm.ai/en/latest/design/hybrid_kv_cache_manager/)

## 6. 동작별 비용 초안 — 층 1개 · decode 1스텝 · 1M (슬라이드 4 · 5 원고)

구조 효과 기준(KV BF16)의 계산값이다. ⚠️는 보강할 항목.

| 방식 (대표 모델) | 저장 / 층 | 읽기 / 층 / 스텝 | 그중 '찾기' 비중 | 접근 패턴 | 상태 |
|---|---:|---:|---:|---|---|
| Full · MLA (DeepSeek-V3) | 1.15 GB | 1.15 GB | 0 | 연속 | ✅ |
| Full · GQA (Qwen3-235B, KV 4 × 128) | 2.0 GB | 2.0 GB | 0 | 연속 | ✅ |
| SWA (gpt-oss, `W` 128) | 수백 KB (고정) | 같음 | 0 | 연속 · 링 버퍼 | 계산 확인 |
| DSA (DeepSeek-V3.2) | 1.28 GB | **0.13 GB** (색인 128 MB + 본 KV 2.4 MB) | **약 98%** | 스캔 연속 + 2,048조각 | ✅ |
| CSA (DeepSeek-V4-Pro) | 약 0.16 GB | 약 17 MB (색인 16.8 MB + 엔트리 0.6 MB) + 최근 창 | 약 97% | 스캔 + 1,024조각 | ⚠️ 정밀도 혼합 |
| HCA (DeepSeek-V4-Pro) | 약 4.5 MB | 약 4.7 MB | 0 | 연속 | ⚠️ 정밀도 혼합 |
| QSA (Qwen3.8-Flash-Next, KV 2 × 256) | 약 2.1 GB (블록 색인 포함) | 약 68 MB (본 KV 4.2 MB + 블록 색인 64 MB) | 약 94% | 스캔 + 512조각 (4토큰 연속) | ⚠️ 블록 키 BF16 가정 (config에 정밀도 표기 없음) |
| Linear · Gated DeltaNet (Qwen3.5) | 약 4 MB (고정) | 약 4 MB 읽기 + 4 MB 쓰기 | 0 | 연속 · 전체 덮어쓰기 | 계산 확인 |
| (참고) LSA · GLM, 10M | 10.24 GiB | 0.17 GiB (Full 10 GiB의 1/60) | — | — | 외부 자료 · 조건 미확인 |

- 하한 시간(H200 4.8 TB/s): Full MLA 1.15 GB → 약 240 µs, DSA 0.13 GB → 약 27 µs (층당, gather · top-k 비효율 제외)
- **모델 전체는 층 구성대로 합산한다.** 예: Qwen3.8-Flash-Next는 48층 중 QSA 12층만 위 QSA 행이고 나머지 36층은 DeltaNet 행이다
- **⚠️ 확인할 것:** LSA 자료의 "기존 희소" 읽기 절감은 약 30배(10 → 0.33 GiB)인데, 우리 DSA 계산은 약 9배에서 포화한다. LSA 자료 수치로 역산한 색인 키는 토큰당 약 32 B, 우리는 128 B(FP8)다 → GLM-5 config로 확인

## 7. 방식 비교표 초안 (부록, LSA 자료 (6)형)

## 9. 차트 규칙

- **한 장에 차트 하나, 계열 4개 이하.** 범례 대신 선 끝 · 막대 옆에 직접 이름을 쓴다
- **방식별 색을 덱 전체에서 고정** — Full 회색 · 고르기(DSA · QSA) 파랑 · 묶기(CSA · HCA) 주황 · Linear · 하이브리드 초록 · LSA(참고) 보라
- 컨텍스트 축은 로그(32K · 128K · 1M · 10M 눈금만), 공개 지원 길이 밖은 점선. 배수 그래프에는 **1× 선**
- 차트마다 **강조할 숫자 하나**만 크게 (예: "1/9", "98%", "배치 4 vs 32")
- 제목 = 질문 또는 결론 문장, 부제 = 기준 한 줄 (§2)
- 계산값은 실선 · 막대, 실측은 점 · 별도 상자. 조건이 다른 공개 결과는 같은 축에 섞지 않는다
- 수식 유도 · 전체 모델 목록 · 커널 세부 · 하이퍼파라미터는 부록으로. **본문의 판단 기준은 "어떤 동작이 얼마를 차지하고, 어떤 HW 요구로 이어지는가"** 다

## 10. 열린 질문 · 리스크

- **정밀도와 구조가 섞인다** — V4의 절감에는 FP8 · FP4 효과가 들어 있다. 구조 효과 그림은 BF16 통일, 실제 사례 그림은 실제 dtype
- **바이트만으로는 시간을 다 설명하지 못한다** — top-k와 흩어진 읽기의 비효율은 계산값에 없다. 실측이 없으면 "하한"이라고 쓰고 선택 B 장에서 정성적으로 짚는다
- **모델 전체로 보면 이득이 줄어든다** — hybrid는 sparse · full 층이 일부뿐이고, 가중치 읽기 · MoE 통신도 있다. 7장에서 "attention 경로 기준"임을 밝힌다
- **LSA는 연구 단계** — 비교 대상이 아니라 "찾기 비용을 줄이는 다음 흐름"의 사례로만 쓴다
- **품질은 깊게 다루지 않는다** — 공개 정확도는 T5에서 조건과 함께 기록만 하고, 자체 평가는 범위 밖임을 부록에 적는다
