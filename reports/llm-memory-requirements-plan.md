# 최신 LLM의 메모리 요구량과 접근 특성 — 보고서 작성 계획

기준일: **2026-10-27** · 현재 단계: 기존 자료 조사와 계획 수정
관련 자료: [기존 분석·논문 검토 노트](llm-memory-related-work.md)

## 1. 목표와 읽는 순서

**최신 LLM이 무엇을 얼마나 저장하고, 어떻게 읽고 쓰는지 직관적으로 보여준다.**

본문은 대표 모델 6~8개와 핵심 도표 4개를 중심으로 작성한다. 계산식·전체 모델 표·GPU 서빙 사례는 부록에 둔다.

1. 모델 본체와 대화 하나의 상태는 얼마나 큰가?
2. 대화가 길어지거나 동시에 여러 대화를 유지하면 얼마나 늘어나는가?
3. 최근 모델은 무엇을 줄였고, 어떤 비용이 남았는가?
4. 가중치 읽기, KV 추가·재조회, 요약 상태 갱신은 어떻게 다른가?

가중치는 “여러 대화가 함께 쓰는 모델 본체”, KV는 “대화마다 쌓이는 작업 메모리”, recurrent state는 “계속 고쳐 쓰는 요약 상태”로 먼저 설명한다. 그래프마다 질문 하나와 해석 한두 문장을 붙이고, 필요한 용어만 그 자리에서 풀어 쓴다.

## 2. 기존 분석을 먼저 활용한다

조사 순서는 **기존 자료의 숫자·도표 확인 → 조건과 누락 항목 확인 → 공식 자료 교차 확인 → 부족한 부분만 계산**이다.

| 우선 자료 | 활용 |

| [2026년 I/O 종설](https://link.springer.com/article/10.1007/s10462-026-11651-1) | 가중치·KV의 데이터 이동과 기존 비교 그림 |

주요 근거는 원문·제작사·저자·엔진 프로젝트 자료로 연결한다. 기사·커뮤니티는 후보 발견에만 쓴다. 공개 페이지의 제목만 확인한 자료와 본문을 확인한 자료를 구분한다.

## 3. 범위와 표본

기본 대상은 **텍스트 요청의 decode 중 보유하는 가중치와 상태**다. prefill의 최대 메모리, 유휴 prefix 보관, speculative decoding의 추가 상태는 별도 한계·문헌 사례로 다룬다.

조사는 8~10개, 본문은 그중 6~8개로 제한한다. FFN의 dense/MoE와 attention의 full/hybrid는 서로 다른 축으로 표기한다.

| 우선 후보 | FFN | Attention·선정 이유 |
|---|---|---|
| Llama 3.1 70B | Dense | GQA 기준 모델 |
| Gemma 3 27B | Dense | local/global 혼합과 window 상한 |
| DeepSeek-V3 | MoE | MLA 기준, 같은 계열의 변화 출발점 |
| DeepSeek-V4.1-Flash | MoE | 압축·층 간 공유·조회형 파라미터·재계산 |
| Qwen3.8-27B | Dense | DeltaNet + full attention의 hybrid |
| Qwen3.8-Flash-Next | MoE | DeltaNet + sparse attention, 대형 n-gram 조회 |
| Kimi K3 | MoE | KDA + MLA hybrid와 대형 가중치 |
| Nemotron 3 Ultra | MoE | Mamba + attention hybrid와 저정밀 배포 |

같은 계열의 전후 비교가 필요하면 DeepSeek-V4-Flash를 보완한다. 초대형 가중치 규모를 더 볼 필요가 있을 때만 Qwen3.8-2.4T-A95B를 추가한다. DeepSeek-V3.2는 “덜 읽어도 저장량은 유지될 수 있다”는 설명 사례로 사용한다.

Llama 8B·Qwen3-Next·Kimi Linear·V4-Pro는 검산·논문 비교에 필요한 경우만 참고한다. 구조 정보가 부족한 Mistral Large 4 preview는 핵심 정량표에서 보류한다. 공개 모델의 대표 사례를 시장 전체의 평균이나 보편적 성장률로 일반화하지 않는다.

## 4. 비교 조건을 먼저 정한다

| 항목 | 본문의 기준 |
|---|---|
| 가중치 정밀도 | **선택한 공식 배포 포맷 1개/모델**. 혼합 정밀도·양자화 부가 정보 포함 |
| 대화 상태 정밀도 | 선택한 배포의 KV dtype 표시. 구조 비교용으로 **KV 16-bit 환산**을 별도 표시 가능 |
| Recurrent state | 구현에서 확인한 dtype 사용. KV를 16-bit로 환산해도 FP32 state까지 임의로 줄이지 않음 |
| 길이 | 32K=32,768, 128K=131,072 tokens. 입력+누적 출력의 현재 보유 길이 |
| 길이 곡선 | 짧은 구간부터 공식 native 최대 길이까지. 확장 설정은 별도 표기 |
| 요청·공유 | 모델 복제본 1개, 독립 대화, prefix 공유 없음, speculative decoding 비활성 |
| 용량 집계 | 고유 tensor·상태 기준. 병렬화 복제·페이지 패딩·예약 pool·임시 버퍼 제외 |
| 단위 | 원본은 byte, 표·그림은 GiB/TiB. GB와 구분 |
| 누락 | 전체 상태를 확인하지 못하면 N/A 또는 부분값. 누락을 0으로 간주하지 않음 |

가중치를 모두 BF16으로 바꾼 표는 기본 산출물에서 제외한다. 실제 배포 포맷의 차이도 용량에 영향을 준다고 설명하고, 이를 순수한 구조 개선이나 동등 품질의 우열로 해석하지 않는다.

본문 용량표의 공통 캡션은 **“선택한 구성의 고유 가중치+상태 용량. 병렬 복제와 실행 부가 비용 제외”**로 한다. 이는 분석 기준값이며 GPU 적재에 충분한 용량을 뜻하지 않는다.

## 5. 무엇을 가중치와 상태로 셀 것인가

### 가중치: 본체·조회형·부가 모듈의 포함 범위를 밝힌다

- **본체:** attention·FFN·공통 embedding 등. 제작사의 backbone 범위와 대응시킨다.
- **조회형:** Engram·n-gram 등. 본체 숫자에 이미 포함되어 있는지 확인하여 이중 계산을 막는다.
- **부가 모듈:** MTP·draft·vision·projector 등. 사용 여부와 실제 적재 여부를 따로 적는다.

기본 가중치 비교는 필수 본체·조회형을 모두 보유하는 경우다. 선택적 MTP·draft는 분리하되, 엔진이 실제로 제외할 수 있다는 근거가 없으면 “제외 후 GPU 상주량”을 확정하지 않는다. 텍스트 요청이라도 vision이 함께 적재되면 그 용량은 적재 사례에 포함한다.

공식 파일 목록·weight index·배포 문서를 우선 사용한다. 한 배포 포맷의 고유 weight shard만 집계하고 중복 포맷·비가중치 파일을 제외한다. **체크포인트 크기와 GPU 상주량은 별도 항목**이다. 집계가 불일치할 때만 관련 tensor·header를 추가 확인한다.

활성 파라미터는 용량 요약표에서 빼고 접근 특성 설명에서 다룬다. prefill/decode 수치가 다르면 단계별로 적고, 이를 실제 weight 읽기 byte로 바로 환산하지 않는다.

[Qwen 공식 카드](https://huggingface.co/Qwen/Qwen3.8-Flash-Next)와 [DeepSeek 공식 카드](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash)는 본체 외 모듈과 활성 범위를 확인할 자료다. [Engram 공식 자료](https://github.com/deepseek-ai/Engram)의 host offload 가능성은 해당 기능의 근거로 쓰되, 특정 모델의 기본 배포 위치로 가정하지 않는다.

### 상태: 길이에 따라 늘어나는 부분과 요청별 상태를 함께 센다

| 구조 | 확인할 내용 |
|---|---|
| GQA·MLA | 실제로 저장하는 K/V·latent·위치 성분. 공유 tensor는 한 번만 집계 |
| Sparse | main KV와 indexer key·보조 저장을 합산. 선택된 토큰 수만으로 저장량을 줄이지 않음 |
| Window·압축 | 실제 보존 범위, 압축 global cache, local cache와 압축용 상태 |
| Linear·SSM·hybrid | recurrent·convolution state의 shape·dtype, 남아 있는 attention KV |
| 층 간 공유·재계산 | cache 소유·공유 관계, 유지하는 상태와 다시 계산하는 상태의 구분 |

고정 크기란 **선택한 기본 추론 방식에서 요청 하나를 이어 가는 최소 상태가 길이에 비례하지 않는다**는 뜻이다. Prefix용 checkpoint, rollback 사본, 페이지 패딩은 추가될 수 있다. [vLLM hybrid cache 문서](https://docs.vllm.ai/en/latest/design/hybrid_kv_cache_manager/)

Global KV, 영구 보관용 cache, 실행 중 전체 상태를 구분한다. 일부 global 수치만 확인된 모델은 그림에서 범위를 명시하고 전체 상태·동시성 지표로 확대하지 않는다.

## 6. 길이·동시성·GPU를 어떻게 다룰 것인가

동시 요청은 “대화 상태를 보유하는 활성 대화 수”로 설명한다. 대기 중인 사용자 수·엔진의 최대 sequence 설정·한 단계의 prefill 토큰 수와 구분한다.

동시 대화 1·8·32개는 직관적인 예시로만 남기고, 모델별 차이는 **“대화 상태의 합이 가중치 용량과 같아지는 대화 수”**로 보여준다.

```text
비교 지점 = 올림(선택한 가중치 보유량 / 해당 길이의 대화 하나 전체 상태)
조건: 독립 대화, 같은 길이·정밀도, 공유·offload·병렬 복제 없음
```

이는 용량의 비중이 바뀌는 눈금이다. **최대 동시 사용자 수, 실행 가능한 batch, 대역폭 병목 전환점이 아니다.** 전체 상태를 확정하지 못한 모델에는 이 값을 제시하지 않는다. 공통 대화 길이의 지원 여부도 확인한다.

GPU는 본문 모델을 고르는 필터로 쓰지 않는다. **H100 8장 공통 서빙 기준을 해제**하고, 검증 가능한 배포 사례만 부록 상자로 둔다. 사례별로 다음을 기록한다.

- GPU·장수·연결, 엔진·버전, 선택한 weight/KV 포맷, 입력·출력 길이.
- TP/PP/EP/DP 구성, 모델 복제 수, KV 복제 배수 또는 실제 shard·replica 배치.
- 가중치·조회형 테이블의 상주 위치, 예약 pool·사용 중 상태·장치별 최대 사용량.
- 문헌 실측인지 계산인지와 근거. 원문에서 빠진 설정은 미공개로 표시.

MLA나 적은 KV head의 복제는 엔진·병렬 방식에 따라 달라진다. “TP8이면 항상 몇 배”로 고정하지 않는다. [SGLang의 DP Attention 사례](https://www.lmsys.org/blog/2025-05-05-large-scale-ep/)

노드 용량 기준선은 필요한 경우 부록에만 둔다. 공식 용량과 실제 사용 가능량을 구분하고, 합산 용량 이내라는 이유만으로 적재 가능하다고 판정하지 않는다. 자체 GPU 실측은 이번 보고서의 기본 작업에서 제외한다.

## 7. 본문 도표 4개와 트렌드 표현

| 도표 | 구성 | 독자가 얻을 것 |
|---|---|---|
| **1. 모델별 용량 비교** | 가중치와 128K 대화 상태를 나눈 두 패널. 크기 차이가 크면 로그축 점 그래프, 정확한 값은 옆 표에 표시 | 모델 본체와 대화 상태를 각각 얼마나 보유하는가 |
| **2. 대화 길이별 상태 곡선** | 대표 4~6개. 비교용 KV 16-bit와 확인한 state dtype 사용. window 상한·native 끝점 표시 | 길이가 늘어날 때 증가 속도가 어떻게 다른가 |
| **3. 상태와 가중치 용량이 같아지는 대화 수** | 32K·128K 비교. 선택한 포맷·전체 상태가 확정된 모델만 | 상태의 용량 비중이 언제 커지는가 |
| **4. 저장·읽기·갱신·대가 표** | 메모리 객체의 접근 특성과 주요 기법을 연결. ↓·조건부·유지와 짧은 설명 사용 | 용량 절감과 읽기·쓰기 변화가 어떻게 다른가 |

공식 배포 포맷과 KV 16-bit 환산을 같은 그림에 표시하면 채운 점·빈 점으로 일관되게 구분한다. 이 표시는 **포맷 구분**이며 출처의 신뢰도나 실측 여부를 뜻하지 않는다. 설명이 복잡해지면 별도 작은 패널로 나눈다.

로그축에는 단위·주요 눈금을 직접 쓰고 모델·곡선을 과도하게 겹치지 않는다. 고정 state가 눈에 보이도록 짧은 길이 구간도 포함한다. 전체·부분 상태, KV 정밀도, 계산/실측을 캡션에서 구분한다.

트렌드는 **같은 계열의 전후 비교**를 중심으로 설명한다. DeepSeek 공식 세대별 global KV 그림 등에는 세대별 dtype와 포함 범위를 붙인다. 구조 효과와 정밀도 효과가 섞인 감소율을 구조만의 성과로 부르지 않는다. 임의 표본의 출시일 산점도·성장률, heatmap·waterfall·가정 기반 상세 트래픽 막대는 기본 산출물에서 제외한다.

## 8. 읽기·쓰기를 설명할 때의 원칙

- Dense/shared weight는 반복 읽기와 batch 재사용, expert는 routing과 활성 집합, 조회형 테이블은 lookup 단위·지역성을 설명한다.
- KV는 새 항목 추가와 과거 항목 재조회, recurrent state는 읽은 상태의 갱신·덮어쓰기를 설명한다.
- 기법은 **작게 저장 / 골라 읽기 / 요약 상태 갱신 / 보관·공유 범위 조정 / 저장 대신 재계산**으로 풀어 쓴다.
- Recompute/replay가 보관량을 줄여도 실행 중 working set·읽기·연산이 모두 같은 비율로 줄어드는 것은 아니다.
- Prefix 공유는 중복 보관과 prefill 재계산을 줄일 수 있다. Decode의 요청별 참조는 남으며, 물리 읽기 절감은 cache·kernel 재사용에 따라 달라진다.
- 용량이 같아지는 대화 수와 읽기 병목의 전환점을 구분한다. 읽기 병목은 기존 분석·문헌의 조건을 붙여 정성적으로 설명한다.

모델별 bytes/step·필요 대역폭을 새로 추정하는 작업은 기본 범위에서 제외한다. MoE routing·커널·on-chip cache의 실측 근거가 없는데도 정확한 트래픽 값처럼 표시하지 않는다. Prefill과 decode의 활성·읽기 특성 차이는 본문에서 짧게 유지한다.

## 9. 근거 확인과 산출물

숫자 표시는 **공식 명시 / 계산 / 문헌 실측** 세 종류로 정리한다. “부분값·미검증·조건부”는 별도 상태 표시다. 문헌에 실린 이론값도 실측으로 분류하지 않는다.

모델 카드·config의 revision과 열람일, 필요한 cache 구현의 commit·엔진 버전, 논문 버전·그림 번호를 보관한다. 기존 계산을 재사용할 때 포함 범위와 dtype를 확인하고, 고정 state·local/indexer·추가 모듈 등 누락된 항목만 보완한다. 불일치가 해결되지 않으면 범위·부분값·N/A로 남긴다.

외부 그림은 원본 조건·출처·재사용 조건을 확인한다. 수치 표가 있으면 표를 우선하고, 그림에서 읽은 값은 근삿값으로 표시한다. 필요한 직접 계산과 도표 생성은 작은 스크립트로 재현 가능하게 남긴다.

```text
reports/
  llm-memory-requirements-plan.md       # 현재 계획
  llm-memory-related-work.md            # 자료 검토·확인 범위
  llm-memory-requirements.md            # 후속 본 보고서
  llm-memory-requirements/
    sources.md                         # URL·버전·범위·그림·문헌 사례
    data/models.json                   # 조건·구성 요소·항목별 근거
    data/memory-results.csv             # 용량·길이·동시성 비교값
    scripts/                           # 필요한 보완 계산·도표 생성
    figures/                           # PNG·SVG
```

작업은 **자료·표본 확정 → 포함 범위·포맷 정리 → 필요한 보완 계산 → 핵심 도표 → 쉬운 본문·수치 검수** 순서다. 계산식과 GPU 설정을 읽지 않아도 주요 표와 그림을 이해할 수 있으면 가독성 기준을 충족한다.
